# FORMFIND — changelog

v1.11.1 - 2026-08-06 - Fixed a real robustness gap, found in the field: if `hardware-bridge.js` fails to load (missing file, wrong dev-server folder, stale cache, MIME-type mismatch — anything), both "Connect Arduino" and "Connect via Wokwi Bridge" silently hung on "Connecting…" forever, since the dynamic `import('./hardware-bridge.js')` call in `ensureHwBridge()`/`ensureWokwiWsBridge()` wasn't wrapped in a try/catch — the promise rejected uncaught and the click handler just stopped running. Wrapped both connect handlers so a failed import now shows a clear, actionable status message and toast ("Could not load hardware-bridge.js — check it's in the same folder as this file") instead of an indefinite silent hang. Reproduced the exact failure (serving index.html without hardware-bridge.js present) and confirmed the new error message appears immediately rather than the button staying stuck.

v1.11.0 - 2026-08-05 - Added a genuinely live Wokwi link, replacing the WebSerial+virtual-COM-port approach after it hit a real Windows wall in the field: com0com's driver reported Status: Error (unsigned, blocked without Test Signing Mode) and Test Signing Mode itself was blocked by Secure Boot policy — a BIOS-level change not worth walking someone into for this. Added `createWebSocketBridge()` to hardware-bridge.js: same external shape as `createHardwareBridge()` (connect/disconnect/connected, same getAngles/onSensorReading/onStatusChange callbacks), but over a plain WebSocket — no OS-level driver, no virtual COM port, works in any browser. Added `arduino/formfind_servo/wokwi_ws_bridge.py`, a small local relay: browser WebSocket on one side, Wokwi's existing RFC2217 server on the other (the RFC2217 half was never the problem — `wokwi.toml` already had it configured since v1.10.0). New "Connect via Wokwi Bridge" option sits in the Physical Rig panel alongside the existing WebSerial "Connect Arduino" button — the WebSerial/com0com path is kept and documented as a fallback, not removed, since it does work on systems where the driver loads cleanly. Testing note: validated the actually-new code fully — FORMFIND's WebSocket client end-to-end against a real running WebSocket server (correct frame format, sensor readings correctly driving Turbulence, clean disconnect, zero console errors) and the bridge script's graceful-failure path (clear error message and clean close when Wokwi isn't reachable, no hang). Building a fully spec-compliant mock RFC2217 server to test that specific leg was a disproportionate rabbit hole for validating a single standard `pyserial.serial_for_url()` call; that half is Wokwi's own long-established, documented server implementation, not new code introduced here.

v1.10.0 - 2026-08-01 - Added a Wokwi circuit embed to the Physical Rig panel: paste a wokwi.com/projects/... link and it renders inline as an iframe, giving a much richer visual reference (real board + servo parts, as wired in that project) than the abstract posts-and-arms 3D preview. Deliberately scoped as a static reference embed, not a live-linked one — looked into whether an embedded Wokwi simulation could receive real-time serial data from the host page (found Wokwi's own `wokwi-client.js`/`message-port-transport.js` prototype for exactly this), but it's explicitly marked "not officially supported" by the Wokwi team, so building against it risked shipping something that silently breaks. Shipped the reliable part instead. Input handling only ever extracts a numeric project ID via regex and builds the iframe `src` from that — the raw pasted text is never used as the src directly, so a malicious-looking paste (tested with a `javascript:` URL) can't become an arbitrary iframe target, only ever `https://wokwi.com/projects/<id>`. Verified the extraction/sanitization logic directly (bad input → rejected with a toast, full URL → correct ID extracted, bare numeric ID → same, injection-shaped input → still sanitized to a plain wokwi.com URL); couldn't screenshot the actual rendered Wokwi content since wokwi.com itself is blocked in the test sandbox (unrelated to the app — confirmed the same for fonts.googleapis.com back in v1.0.0's testing).

v1.9.0 - 2026-08-01 - Extracted the WebSerial connection logic (connect/disconnect, the servo send loop, the sensor read loop, all error handling) out of index.html into a new shared/hardware-bridge.js — a small reusable ES module any of the generative-design-tools can import to drive the same physical rig without re-implementing the plumbing (protocol, error handling, and reader cancellation had all been copy-paste candidates otherwise). index.html now just supplies three callbacks — getAngles (computeServoAngles, unchanged), onSensorReading, onStatusChange — dynamically imported the same way three.js already is, since the main script isn't itself a module and static `import` statements only work inside one. One real bug caught while writing the module: the top-of-file doc comment used a nested `/* ... */` inside its own `/* ... */` block for an inline code example — JS comments don't nest, so the outer docblock closed at the first `*/` it hit and everything after was parsed as a syntax error. Fixed by switching the inline example to `//` comments. The module's send loop now owns its own `setInterval`, independent of the render loop entirely — index.html's tick() no longer calls a throttled send function at all. Re-verified the full connect → servo frames → sensor reading → disconnect cycle end-to-end against a mocked bidirectional serial port after the refactor, byte-for-byte the same behavior as v1.8.0. `audit_deploy.js` now also reads hardware-bridge.js when present and checks its internals (reader cancellation, sensor-line parsing, interval-based sending) in addition to index.html no longer holding a duplicate copy of the connection logic.

v1.8.0 - 2026-08-01 - Closed the loop: the Arduino connection is now bidirectional. Servo commands still flow browser→Arduino as before; a new sensor reading flows Arduino→browser via `readHardwareLoop()`, a `TextDecoderStream`-piped read loop parsing `S<analogRead 0-1023>\n` lines sent every 50ms by the sketch. A new "Sensor drives" dropdown (Off / Turbulence / Speed) in the Physical rig panel routes incoming readings into `engine.turbulence` or `engine.speed` — the corresponding slider moves live to reflect it, same as if the person had dragged it themselves. A potentiometer or photoresistor next to the physical rig becomes a real input into what's on screen, not just a mirror of it. Updated `arduino/formfind_servo/formfind_servo.ino`: reads `SENSOR_PIN` (default A0) on a `millis()`-based non-blocking timer alongside the existing servo-command parsing, with wiring notes for both a potentiometer and a photoresistor voltage-divider. `disconnectHardware()` now cancels the reader before closing the writer and port; an unexpected read failure (e.g. unplugged cable) surfaces the same "Lost connection" toast as a write failure and cleans up consistently. Verified end-to-end with a mocked bidirectional serial port (a real `ReadableStream` feeding simulated sensor values): confirmed the dropdown correctly routes 0/1023 sensor extremes to the full Turbulence (0-2) and Speed (0.2-2.5) ranges, servo output keeps flowing concurrently with sensor input with no interference, and disconnect cleanly cancels the read loop.

v1.7.0 - 2026-08-01 - Replaced the flat bar-chart hardware simulator with a literal 3D preview: a dedicated Three.js scene showing a row of pedestals, each with a servo arm swinging a small sphere, in an orthographic elevation view (fixed camera framing computed from required vertical reach so the arm/sphere never clips out of frame regardless of servo count or container width) — plus an "Angled view" toggle for a 3/4 perspective. Critically, this isn't just a redraw of the same instant angles: added realistic servo speed simulation (`HW_SERVO_SLEW_DEG_PER_SEC`, ~300°/s, a typical standard hobby servo's real top speed) that limits how fast the simulated arms can actually move, using true delta-time integration rather than the throttled ~20Hz serial-send rate — so this is the first place in the app that can actually tell you whether a motion is too fast for real hardware before any hardware exists. Rebuilds automatically when servo count changes (carries over current angles for continuity rather than snapping back to neutral). Verified the slew limit numerically (≤15° of movement in a 50ms window against the 300°/s cap) and fixed a camera-framing bug caught in testing where the wide, short viewport aspect ratio was clipping the arms/spheres out of the visible frame. Updated the in-app help text to match.

v1.5.0 - 2026-08-01 - Added an on-screen servo simulator for testing the hardware bridge without any physical rig: a "Show simulated servo bars" checkbox in the Physical rig panel renders one bar per servo, driven by the exact same `computeServoAngles()` call the real WebSerial path uses, at the same throttled ~20Hz — so it's a true preview of what the Arduino would receive, not a separate mock. Works with or without a real connection, and independently of servo count (rebuilds the bar row when the count changes). No install required, unlike the deeper option (a virtual serial port pair, e.g. com0com on Windows or socat on Mac/Linux, feeding a small script that prints or visualizes the actual received frames) which tests the real WebSerial connect flow end-to-end but needs OS-specific setup — that's the next level up if the on-screen bars aren't enough.

v1.4.0 - 2026-08-01 - Added a physical hardware bridge: FORMFIND can now drive a real rig of hobby servos over WebSerial (Chrome/Edge only), mirroring whatever's on screen live — ambient, manual, or audio, whatever mode is active. Samples `state.currentY` (the same per-sphere heights used for rendering) into N evenly-spaced column bands, averages each band, maps the practical height range [-2, 4] to a servo-safe angle range [20°, 160°] (staying off the 0/180 end-stops), and writes one line per frame — `A<angle0>,<angle1>,...\n` — throttled to ~20Hz regardless of the render framerate, since servos can't usefully move faster than that and it keeps the Uno's serial buffer from backing up. Servo count is adjustable live from the panel (1-16) and must match `NUM_SERVOS` in the paired Arduino sketch. Added `arduino/formfind_servo/formfind_servo.ino`: parses the same line protocol, constrains every angle to 0-180 before writing to the servo (defense in depth even though the browser already clamps), guards against buffer overflow on malformed input, and centers all servos on boot. Feature-detects `'serial' in navigator` and disables the connect button with an explanatory status line on unsupported browsers. Tested with a mocked WebSerial port (Object.defineProperty override, since headless Chromium's real WebSerial hangs waiting for a device picker) — verified correct baud rate, frame format, angle clamping, live servo-count changes, and clean disconnect.

v1.3.0 - 2026-08-01 - Added basic transport controls. Single file: rewind 10s, play/pause, stop (pauses and resets to 0:00), forward 10s. Stems: the same four controls apply to all loaded stems simultaneously via `seekStems()`/`stopStems()`, keeping them in sync since they're separate `<audio>` elements with no shared clock. Microphone gets an explicit "Stop microphone" button instead (no seek/stop concept for a live stream — releases the mic). Leaving Audio mode now also resets the transport UI (hides rewind/play/stop/forward rows, resets status text) so re-entering doesn't show stale button states from the previous session.

v1.2.1 - 2026-08-01 - Fixed a real bug (not user error, confirmed on the user's actual hardware): with all 4 stems loaded, every sphere rendered pure black regardless of mode — including plain ambient/manual, no audio involved. Root cause: per-instance `vertexColors` on the InstancedMesh (introduced in v1.2.0 for stem coloring) rendered near-black in this three.js build. Isolated methodically — ruled out audio/energy state, ruled out color-space/sRGB conversion, ruled out metalness/roughness, ruled out material caching, and finally ruled out MeshStandardMaterial's lighting model entirely by reproducing the same near-total darkness on a plain unlit MeshBasicMaterial with a pure-white instance color (should have been a no-op multiply) — confirming the instanced-color path itself is broken here, not any specific color value or lighting interaction. Replaced the single vertexColors-driven mesh with 5 separate InstancedMesh objects (gray + one per stem), each using a normal solid `material.color` — a plain, well-supported pattern with no per-instance color buffer involved. Every sphere's transform is written into whichever category mesh matches its current dominant-stem column each frame, and each mesh's `.count` is set to how many spheres landed in it that frame. Re-verified brightness returned to normal (peak channel value 255, matching pre-bug renders) in ambient, manual, and stems modes, and re-confirmed actual stem-colored pixels render correctly via direct pixel inspection. Added `audit_deploy.js` checks to guard against reintroducing `vertexColors` on the sphere material.

v1.2.0 - 2026-08-01 - Added stem coloring: upload up to 4 already-separated stem files (vocals/drums/bass/other — separated externally via Demucs/LALAL.AI/Moises, FORMFIND does not separate audio itself) and each gets its own AnalyserNode + per-column log-scaled energy, same mapping as the single-source EQ. Per-column heights now sum across whichever stems are loaded; each sphere's color blends from neutral gray toward whichever stem dominates that column's energy at that moment (gray = quiet, full stem color = that stem clearly leading). Beat detection now prefers the drums stem's energy when present (falls back to bass, then to the old single-source bass-band heuristic) — a real transient signal instead of an approximate one. Added a legend (colored dot + label per stem) and a live "Loaded: X, Y. Not provided: Z." status line. Single-file/mic and stems input are mutually exclusive — loading one tears down the other's audio graph (`disconnectAudioSource()` / `disconnectStems()`), and switching away from Audio mode entirely releases both the mic and any stem sources. Sphere material switched to `vertexColors:true` with a white base color so per-instance `instanceColor` (initialized to the original steel gray) drives the visible tint without changing the non-audio-mode look. Extracted `accumulateColEnergy()` so the log-scaled bin→column mapping isn't duplicated between the single-source and per-stem code paths. Guarded the per-stem load handler against a race where switching to a single file/mic while a stem was still decoding could let that stem's UI update land after `resetStemsUi()` had already cleared it — checks `audioEngine.stemsActive` after the await before touching the DOM.

v1.1.0 - 2026-08-01 - Added an Audio mode: upload a local audio file or use the microphone (Web Audio API AnalyserNode) to drive the field. Per-column frequency energy is mapped log-scale across the grid (bass on the left, treble on the right, like a live equalizer) via a smoothed EMA per column. Bass-band energy also feeds a simple onset/beat detector (instantaneous bass vs. a slow rolling average, with a cooldown) that fires a decaying "shimmer" pulse across the whole field on each detected beat. Existing Speed/Turbulence sliders now also scale the audio-driven amplitude. Leaving Audio mode releases the microphone stream and pauses file playback (`disconnectAudioSource()`); a `<audio>` element can only ever get one `MediaElementSourceNode`, so the file source node is created once and reused across file swaps. Extracted the resolve/audio height scale into a shared `PEAK_HEIGHT` constant instead of a duplicated magic number.

v1.0.0 - 2026-08-01 - Initial build: a 44×22 grid of instanced spheres (Three.js) drifts through a sine-based noise field and can resolve into text or one of four presets (circle, car profile, skyline, blob) by rasterizing the target onto an offscreen canvas and sampling per-cell brightness into height targets. Ambient mode auto-cycles chaos → shape → chaos indefinitely; Manual mode lets the user type text or pick a preset and scramble back to chaos on demand. Fixed a temporal-dead-zone bug during initial build where `render()` ran during boot before the `engine` state object was declared further down the same script — reordered so engine/state declarations precede the view router and boot IIFE (same class of bug as Facade Lens v1.9.0, per NEW_PROJECT_TEMPLATE.md §8).
