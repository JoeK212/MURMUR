# FORMFIND — changelog

v1.16.0 - 2026-08-07 - Both stick-figure rigs (v1.15.0) felt unanimated per user feedback — each figure only had one small arm moving, everything else (torso, legs, head, second arm) sat frozen, so the row read as mostly static even while genuinely receiving live data. Added idle secondary motion to both, phase-offset per figure so the row reads as a wave rather than a lockstep twitch: a gentle vertical bob, a leg-sway (weight-shifting in place), and a slower resting-arm sway. This is explicitly decorative — driven by elapsed time, not by any servo or firmware data — and documented as such in both the code comments and (for the avr8js dashboard, where accuracy is the whole point) directly in the page's own visible copy, so nobody mistakes the bob/sway for real signal. The one piece of real data — each figure's single driven arm — is completely untouched: same rotation formula, same real angle values, in the 3D preview still the same ~300°/s slew-rate limiting from v1.7.0. In the 3D preview, idle motion is computed each frame in updateHwSimulator() from the existing requestAnimationFrame timestamp (already available as `now`), applied to newly-tracked per-figure references (figureGroups/legLefts/legRights/restingArms, alongside the existing armPivots). In the avr8js dashboard, idle motion is pure CSS (@keyframes + animation-delay per figure) rather than JS, so it costs nothing on the WebSocket/render loop that's actually carrying real data. Also enlarged both figures for visibility — the SVG dashboard's figures scaled up ~30% (viewBox 52×84 → 70×116, figure spacing tightened to fit) since part of the "not much going on" impression was simply that the arm swing was hard to see at the old size. Verified the full protocol round-trip still passes unchanged after the rewrite (109 sensor lines in 5.5s, commanded angles decoding correctly) — confirms the idle-motion changes are additive and didn't touch the data path.

v1.13.0 - 2026-08-07 - Gave `avr8js_sim_bridge.js` (v1.12.0) a visual: it now also serves a small live browser dashboard at `http://localhost:8766` — 8 SVG servo arms rotating in real time, matching FORMFIND's own dark palette (`--paper`/`--ink`/`--accent` etc., copied from index.html's CSS variables for visual consistency across the tool suite). Motivated directly by user confusion after v1.12.0 shipped terminal-only: the user pointed at the *embedded Wokwi iframe* at the bottom of the Physical Rig panel and asked why its servos weren't moving — that panel is FORMFIND's pre-existing static reference embed (v1.10.0), deliberately never live-linked, and unrelated to either WS bridge backend; the actual confirmation that v1.12.0 was working live only in a scrolling terminal line was too easy to miss entirely. The new dashboard is a second, independent, read-only piece bolted onto the existing bridge process — a plain `http` server plus a second `ws.Server` attached to it, broadcasting `{angles, simTime, sensor, formfindConnected}` as JSON at ~20Hz (same cadence as the firmware's own sensor-send interval) to any connected browser tab; nothing here feeds back into the firmware or into FORMFIND itself. Every angle it draws is the same `currentAngles` value already being measured from real PWM pulses for the terminal readout — not a separate/simplified computation, so the two displays can't drift from each other or represent different things. Deliberately distinguished from FORMFIND's existing "Show simulated rig" checkbox (v1.5.0) in both the in-app copy and AVR8JS_SETUP.md: that checkbox mirrors FORMFIND's own on-screen state with no firmware involved at all, so it can never surface a firmware bug; this dashboard only shows what the real compiled firmware actually did with a given command, so a firmware-side bug shows up here the same way it would on real hardware. Verified end-to-end: a mock dashboard WS client receives the correct neutral-angle boot state before FORMFIND connects, `formfindConnected` flips true the instant a FORMFIND-side client connects (independent of the dashboard's own connection), and a real `A20,160,90,45,135,0,180,60` command sent on the existing 8765 protocol shows up correctly decoded in the dashboard stream — not echoed from the command, measured from the same PWM-pulse decode path already covered by v1.12.0's tests. Added `--dashboard-port=<port>` and `--no-dashboard` flags; the dashboard's own WebSocket reconnects automatically if the bridge script restarts, so a browser tab left open survives a bridge restart.

v1.12.0 - 2026-08-07 - Added a second backend for the WebSocket hardware bridge: `formfind_servo/avr8js_sim_bridge.js`, which runs `formfind_servo.ino`'s actual compiled firmware inside `avr8js` (the open-source MIT-licensed AVR core that powers Wokwi itself — github.com/wokwi/avr8js) instead of relaying to Wokwi's cloud. Speaks the exact same WebSocket line protocol on the same default port (8765) as the existing `wokwi_ws_bridge.py`, so FORMFIND's "Connect via Wokwi Bridge" button and its `ws://localhost:8765` default work with either script unchanged — no FORMFIND-side protocol or UI logic changed, just a second thing that can sit on the other end of that button. Built to remove every dependency that broke during v1.11.0's testing (Wokwi VS Code extension, RFC2217, virtual COM ports, driver signing) — this backend needs none of them, just Node.js. The firmware itself is not reimplemented or mocked: `build_hex.sh` compiles the real `formfind_servo.ino` with the real AVR toolchain (avr-gcc/avr-libc) against the real Arduino core and Servo library sources, producing the identical `.hex` a real Arduino would run; the sim bridge loads that hex into avr8js and runs it. Servo angles aren't computed from the outgoing command — they're measured from the actual PWM pulse widths the firmware's real Servo-library Timer1 ISR puts on the simulated GPIO pins, decoded back to degrees, so a firmware bug in angle handling would show up here exactly as it would on real hardware. A0 has no real potentiometer behind it in this mode, so the script feeds the ADC a synthetic default sweep (0–1023 over ~12s, override with `--sensor=<value>` or `--sensor=off`) purely so the sketch's own `analogRead()`-driven sensor loop has something to report; this is the one piece that's a stand-in rather than real hardware, and is documented as such. Execution is paced to real wall-clock time (avr8js's own demo runs flat-out and only reports a speed percentage, which would flood the ~20Hz sensor stream far faster than FORMFIND expects) via a real-time-catch-up loop with fine-grained substeps so queued serial bytes get injected at genuine 115200-baud timing rather than dropped. Verified end-to-end against a real WS client speaking hardware-bridge.js's exact protocol: sensor stream lands at ~19.8Hz over a 5.5s window (109 lines, expected ~110), servo angles commanded via `A45,90,135,0,180,60,120,150\n` round-trip through real UART RX injection → the firmware's own `handleLine()` parser → real bit-banged PWM → pulse-width decode and come back exactly matching; out-of-range angles (999, -50) get clamped to 180/0 by the firmware's own `constrain()` call (confirmed, not reimplemented client-side); a malformed non-`A`-prefixed line is correctly ignored with no spurious motion, matching `handleLine()`'s own guard. Added `AVR8JS_SETUP.md`-equivalent documentation inline in `avr8js_sim_bridge.js`'s header and cross-referenced it from both the Physical Rig panel label and the in-app Help modal, alongside the existing Wokwi-relay option — framed as two backends for the same button, not a replacement.

v1.4.0 - 2026-08-01 - Added a physical hardware bridge: FORMFIND can now drive a real rig of hobby servos over WebSerial (Chrome/Edge only), mirroring whatever's on screen live — ambient, manual, or audio, whatever mode is active. Samples `state.currentY` (the same per-sphere heights used for rendering) into N evenly-spaced column bands, averages each band, maps the practical height range [-2, 4] to a servo-safe angle range [20°, 160°] (staying off the 0/180 end-stops), and writes one line per frame — `A<angle0>,<angle1>,...\n` — throttled to ~20Hz regardless of the render framerate, since servos can't usefully move faster than that and it keeps the Uno's serial buffer from backing up. Servo count is adjustable live from the panel (1-16) and must match `NUM_SERVOS` in the paired Arduino sketch. Added `arduino/formfind_servo/formfind_servo.ino`: parses the same line protocol, constrains every angle to 0-180 before writing to the servo (defense in depth even though the browser already clamps), guards against buffer overflow on malformed input, and centers all servos on boot. Feature-detects `'serial' in navigator` and disables the connect button with an explanatory status line on unsupported browsers. Tested with a mocked WebSerial port (Object.defineProperty override, since headless Chromium's real WebSerial hangs waiting for a device picker) — verified correct baud rate, frame format, angle clamping, live servo-count changes, and clean disconnect.

v1.2.1 - 2026-08-01 - Fixed a real bug (not user error, confirmed on the user's actual hardware): with all 4 stems loaded, every sphere rendered pure black regardless of mode — including plain ambient/manual, no audio involved. Root cause: per-instance `vertexColors` on the InstancedMesh (introduced in v1.2.0 for stem coloring) rendered near-black in this three.js build. Isolated methodically — ruled out audio/energy state, ruled out color-space/sRGB conversion, ruled out metalness/roughness, ruled out material caching, and finally ruled out MeshStandardMaterial's lighting model entirely by reproducing the same near-total darkness on a plain unlit MeshBasicMaterial with a pure-white instance color (should have been a no-op multiply) — confirming the instanced-color path itself is broken here, not any specific color value or lighting interaction. Replaced the single vertexColors-driven mesh with 5 separate InstancedMesh objects (gray + one per stem), each using a normal solid `material.color` — a plain, well-supported pattern with no per-instance color buffer involved. Every sphere's transform is written into whichever category mesh matches its current dominant-stem column each frame, and each mesh's `.count` is set to how many spheres landed in it that frame. Re-verified brightness returned to normal (peak channel value 255, matching pre-bug renders) in ambient, manual, and stems modes, and re-confirmed actual stem-colored pixels render correctly via direct pixel inspection. Added `audit_deploy.js` checks to guard against reintroducing `vertexColors` on the sphere material.

v1.1.0 - 2026-08-01 - Added an Audio mode: upload a local audio file or use the microphone (Web Audio API AnalyserNode) to drive the field. Per-column frequency energy is mapped log-scale across the grid (bass on the left, treble on the right, like a live equalizer) via a smoothed EMA per column. Bass-band energy also feeds a simple onset/beat detector (instantaneous bass vs. a slow rolling average, with a cooldown) that fires a decaying "shimmer" pulse across the whole field on each detected beat. Leaving Audio mode releases the microphone stream and pauses file playback (`disconnectAudioSource()`); a `<audio>` element can only ever get one `MediaElementSourceNode`, so the file source node is created once and reused across file swaps.
