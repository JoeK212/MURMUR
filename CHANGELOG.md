v1.24.1 - 2026-08-07 - User reported the embedded "Show simulated rig" preview (v1.24.0) was dominated by a blown-out white blob under real audio (Speed 1.8, Turbulence 1.4, Audio mode). Root cause: the renderer had no tone mapping set (three.js defaults to NoToneMapping), so once a handful of the additive-blended particle sprites overlapped, every RGB channel just hard-clipped at 1.0 — reads as flat white, and gets worse the busier/more energetic the source audio is, which is exactly when the effect should be most colorful. Set `renderer.toneMapping = THREE.ACESFilmicToneMapping` (exposure 0.9) + `outputColorSpace = THREE.SRGBColorSpace` on the hwSim renderer specifically (main stage renderer untouched — it uses opaque materials, not additive blending, so it never had this problem) so overlapping highlights compress instead of clipping to white. Also reduced the raw amount of overlap contributing to it: particles per emitter 34→22, sprite texture's peak alpha 1.0→0.85 (falloff stop 0.55→0.4), particle size energy formula (1.4+energy×3.4)→(1.1+energy×2.4), marker emissive flash 2.0→1.4. Scoped entirely to the embedded preview's renderer/particle tuning — no data pipeline or camera changes.

v1.23.1 - 2026-08-07 - User reported "I don't see bursts" on v1.23.0's new particle dashboard. Real root cause: the vertex/fragment shader strings were built as `[...].join('\n')`, but that literal text had to survive being embedded inside avr8js_sim_bridge.js's own outer template literal (which processes backslash escapes as it builds the returned HTML), then be re-parsed as JS source by the browser. The escaping needed to survive two parse layers got mismatched, so the browser ended up with literal `\n` text (not real newlines) as the join separator — malformed GLSL, so the ShaderMaterial failed to compile and the entire particle Points mesh silently rendered nothing. Fixed by joining shader lines with a plain space instead of a newline (GLSL doesn't need line breaks between statements here — no `#` preprocessor directives are used, semicolons/braces already delimit everything), which sidesteps the escaping problem entirely rather than trying to get the newline escaping right. Verified the built shader string directly (not just "it parses") by joining the actual line array and reading the output GLSL text. Also tuned the burst itself to be unmistakable now that it's actually rendering: particle speed baseline 0.9→2.6 (energy multiplier 4.2→9.5), lifetime shortened (0.7–1.8s → 0.45–1.2s) so fast particles read as a burst arc instead of a slow drift, base point size 1.1→2.2 (energy multiplier 3.2→6.5), and the point-size camera-distance constant 320→420 for bigger dots overall.

Also addressed: "number of servos does not change." Not a regression — this dashboard's emitter/marker count has been hard-fixed at 8 since v1.12.0, taken directly from `SERVO_PIN_MAP` (the real compiled formfind_servo.ino's actual pin list), and is deliberately decoupled from FORMFIND's UI "servo count" field, which (per v1.20.0) only ever drove real/external hardware output. Changing it here would mean either faking emitters with no real angle data behind them (breaks this dashboard's whole "every number here is real" premise) or rebuilding/reflashing the .hex with a different pin count — flagged to user rather than silently changed.

v1.21.0 - 2026-08-07 - User reported everything running sluggish (both the sim and the main kinetic view) plus vocals out of sync with instruments, right after v1.20.0's embedded firmware simulator shipped. Both real bugs, both fixed at the root rather than papered over.

**Sluggishness:** v1.20.0's embedded firmware simulation was running the real per-cycle AVR CPU emulation synchronously on the main thread, every render frame — genuine, measurable work (an instruction-stepping loop advancing up to tens of thousands of cycles per frame) directly competing with the kinetic-sculpture render loop and with <audio> element scheduling for main-thread time. Moved the entire simulation into a dedicated Web Worker: same CPU/peripheral setup, same PWM-pulse decode, same hex — just running on its own thread now, self-paced off real wall-clock time via its own `performance.now()`-based tick loop (independent of the main thread's frame rate, same real-time-pacing pattern `avr8js_sim_bridge.js` already used from a terminal). The worker loads `avr8js` from the full CDN URL directly (not via the page's import map — worker-scoped import map support is inconsistent across browsers) and communicates via `postMessage`: commands go out throttled to ~20Hz (no need to post a new command every single render frame), decoded angles come back the same way and get read by the main thread at near-zero cost — `updateHwSimulator()` no longer does any CPU emulation itself, just reads the worker's last-known angles.

Testing this surfaced a real bug in the test harness, not the shipped code: an early verification attempt extracted the worker's source via raw text slicing, which skips the browser's own template-literal escape processing (`\\n` → `\n`) that a real `<script>` parse performs automatically — the shipped file was correct throughout. Once the extraction went through actual JS evaluation (matching what a browser does), verification passed cleanly: three consecutive full runs, sequential commands over time, zero degrees of difference between commanded and decoded angles on every check.

**Stem desync:** a genuinely separate, pre-existing bug surfaced by the sluggishness — stems (vocals/drums/bass/other) are four independent `<audio>` elements that were only ever aligned once, at load time (`updateStemsFrame` had no continuous correction), so they could drift apart during playback even under normal conditions, worse when main-thread stalls delayed each element's own playback scheduling unevenly. Added periodic drift correction: every 0.5s, if any playing stem's `currentTime` has drifted more than 80ms from the first playing stem, snap it back in line. Threshold and check interval both chosen to avoid over-correcting on ordinary jitter (which would itself cause an audible micro-stutter) while still catching real drift before it's noticeable.

`avr8js_sim_bridge.js` and its own dashboard are unaffected by any of this — independent Node process, never touched the main thread to begin with.

v1.19.0 - 2026-08-07 - Two fixes from user feedback: the main kinetic-sculpture stage had no way to recover a lost view after panning/zooming with OrbitControls, and the simulated-rig preview's "Angled view" sometimes clipped figures out of frame while also just reading as visually flat.

Verified the fit-distance math directly (n=8 → ~9.8 units, n=16 at the servo-count field's max → ~18.9 units, both comfortably inside the camera's 0.1–60 near/far planes) rather than just eyeballing it.

v1.18.0 - 2026-08-07 - After v1.17.0 the user tested with real audio playing (Black Sabbath - Supernaut) and reported the rig was "still very stagnate" despite the six new decorative/real-data enhancements. Rather than add a seventh flourish, found and fixed the actual root cause in `computeServoAngles()`: it mapped each band's average sphere height against a fixed absolute window (`HW_HEIGHT_MIN=-2` to `HW_HEIGHT_MAX=4`) that was calibrated for the general case across all modes, but in practice a given song/section's real per-band signal usually only occupies a narrow slice of that window — so the resulting angles barely spread out even while the audio underneath was genuinely dynamic. This is the same function used both for the 3D preview (via `updateHwSimulator`) and as the literal `getAngles` callback wired into `hardware-bridge.js` for real hardware and the avr8js WS bridge, so the fix benefits all three consumers from one change, no per-consumer patching needed.

Fix: each band now tracks its own recent floor and ceiling (fast-attack/slow-release envelope followers — `HW_AGC_RISE=0.35` per adapting step, `HW_AGC_FALL_PER_SEC=0.55` relaxing back over about 2 seconds) and maps the current value against THAT adaptive range instead of the fixed one, so a quiet verse and a loud chorus both use the full 20°-160° swing. A span floor (`Math.max(0.5, ...)`) keeps near-silence from getting amplified into jittery noise. Self-timed internally (`performance.now()`-based dt, not a parameter) since the function is called from two different timing sources — `requestAnimationFrame` for the 3D preview, and hardware-bridge.js's own `setInterval` for real/simulated hardware — and needed to work correctly from either without the caller knowing about the AGC state.

Verified with a standalone extracted-logic test before shipping: the same narrow-range signal that produced the stagnant screenshot (oscillating in a 0.3-1.1 band, well within -2..4) produced only an 18° angle swing under the old fixed mapping and an 87° swing under the new adaptive one; a near-silent signal (avg ~0.02) stayed pinned near a single angle rather than jittering, confirming the span floor works.

Second change: wired the real beat-onset signal (`audioEngine.beatPulse`, already computed for the main field's shimmer effect but never used anywhere near the rig) into a synchronized hop across the whole row of figures on every detected beat — `beat = engine.mode==='audio' ? audioEngine.beatPulse : 0`, zero outside Audio mode so it never fakes motion when there's no real beat to react to. This is 3D-preview-only: the avr8js dashboard is a separate Node process with no access to FORMFIND's audio engine, so there's no real beat data to wire in there — noted as a real limitation, not silently skipped.
