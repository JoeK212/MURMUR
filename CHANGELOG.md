v1.39.3 - 2026-08-10 - User reported: the simulated rig shows activity when nothing is playing or active. Verified live via Claude in Chrome against the app's own real running state, not simulated.

Root cause: `computeServoAngles()`'s per-band auto-gain tracks each band's own recent min/max, then maps the current average height into that window. When a band's signal goes genuinely flat (idle, nothing playing), its min and max both converge onto the same resting value — but the *convergence itself* is asymmetric: whichever bound the average is approaching from snaps onto it almost immediately (single-step `Math.min`/`Math.max` cap), while the opposite bound only relaxes slowly (0.55/s). So for most of that relax period — and, worse, once fully converged and the 0.5 floor-on-span kicks in — the window ends up anchored with the resting value sitting at its very *bottom* edge (`mapRange(avg, hwAgcMin, hwAgcMin+span, ...)`), not centered on it. A flat, silent signal was being mapped to `HW_ANGLE_MIN` (a full-scale extreme, ~78% deviation from neutral) instead of 90° (true rest) — and since the rig's glow/particle "energy" is driven directly by deviation-from-neutral, an idle rig looked permanently, indefinitely active. Confirmed live: pulled the actual running app's converged `hwAgcMin`/`hwAgcMax`/real sphere-field averages and fed them through the old formula (all bands → 20°) versus the fixed one (all bands → 90°) side by side against the same real state.

Fixed at the root: window is now centered on the tracked range's own midpoint (`mid ± span/2`) rather than anchored at `hwAgcMin`. Algebraically identical to the old formula whenever the span isn't floored (real, live dynamic range maps exactly as before) — only differs in the degenerate flat/silent case, where a converged average now lands at the window's center (neutral 90°, zero deviation) instead of its edge.

v1.39.2 - 2026-08-08 - User reported: "the fireworks do the same thing when i stop the music." Real bug, precisely traced from the report itself rather than guessed at.

Root cause: the Stop button only ever called `audioEl.pause()` and reset `currentTime` — it never touched `audioEngine.active`, which stays true, so `updateAudioFrame()` kept calling `analyser.getByteFrequencyData()` every frame regardless. An AnalyserNode doesn't reset itself just because its source stopped feeding new samples — it holds whatever was in its last FFT window. So after Stop (or Pause — same underlying issue, `audioEl.paused` either way), the whole reactive pipeline (level, bass/beat detection, per-column energy driving the servo angles) kept reading that frozen last-real-moment snapshot forever, which is exactly "does the same thing" — not a metaphor, literally the same numbers, indefinitely.

Fixed at the root in both `updateAudioFrame()` and the stems variant `updateStemsFrame()`, rather than patching individual buttons (Stop, Pause, a track simply ending, or any other way a source can go quiet all hit the same code path): detect `audioEl.paused` and explicitly decay level/levelSmooth/bassEMA/beatPulse/colEnergy toward zero (exponential, ~6/s) instead of reading the stale analyser. Smooth rather than an abrupt cut, and it now correctly covers Pause fading out gracefully too, not just Stop.

Verified: script parses clean, confirmed the stems object's field name (`audioEl`) actually matches what the fix reads before shipping it, rather than assuming.

v1.38.2 - 2026-08-08 - User confirmed live (own foregrounded tab, not just my automated testing) that the Simulated rig's fireworks stay basically the same regardless of what the sphere field is actually doing. Real bug, root-caused decisively rather than guessed at.

Traced it through several rounds of live instrumentation via Claude in Chrome — including one dead end worth recording: a first attempt moved the per-tick serial byte-feed check outside the CPU cycle-catchup substep loop, reasoning that decoupling it from cycle throughput would guarantee forward progress. Tested live before shipping it and found it was actually a regression (cut real feed opportunities per tick() call from "many, once per substep" down to "one, no matter how many substeps ran") — reverted rather than keep something that looked cleverer but measured worse.

Actual root cause, confirmed by injecting a debug-introspection build of the exact worker source into a fresh isolated Worker and reading its internal state directly: `MAX_CATCHUP_SEC = 0.25` let a single tick() call try to simulate up to 4,000,000 AVR instructions before returning. This JS AVR emulation can't execute that many instructions in anything close to real time inside a Worker — so tick() itself was only getting called roughly once every 400-600ms in practice (each call busy catching up), not its intended ~4ms. rxQueue was observed growing over real time even while usart.rxBusy sat false the whole time, meaning bytes were being consumed, just at a small fraction of the rate real serial timing needs — a full 8-servo command line effectively never finished arriving, decoded angles barely budged off their 90° power-on default, and the fireworks preview looked frozen no matter how much the sphere field changed. Cut MAX_CATCHUP_SEC to 0.01 (25x smaller); confirmed live that a full command now drains from the queue and decodes correctly within about a second, matching the sent values almost exactly.

Applied the identical fix to the standalone avr8js_sim_bridge.js (Node bridge script) for consistency — it has the same constant and the same theoretical risk, even though Node's V8 hadn't been observed actually hitting it in practice; no real cost to shipping the safer value there too rather than leave a proven-risky constant sitting unfixed in a near-identical copy of the same loop.

Verified: index.html's inline script and the standalone bridge's outer file both parse clean; booted the standalone bridge server end-to-end post-fix.
